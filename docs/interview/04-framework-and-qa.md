# Архитектура тестов и QA-процесс (на примере проекта)

> Этот файл — про то, как отвечать на вопросы «как вы строите тестирование»,
> «как обеспечиваете стабильность», «что бы улучшили». Здесь же — вопросы по коду
> тестового фреймворка.

## 1. Слои тестов в проекте

```
                 ┌──────────────────────────────┐
   E2E (6)       │ Playwright: UI + реальный API │  медленно, дорого
                 ├──────────────────────────────┤
   API (18)      │ TestRestTemplate → Tomcat     │  быстро, стабильно
                 ├──────────────────────────────┤
   Unit (11)     │ клиент AI, локализация        │  очень быстро
                 └──────────────────────────────┘
```

| Уровень | Что проверяем | Файлы | Кол-во |
| --- | --- | --- | --- |
| Unit | парсинг ответа AI, ошибки провайдера, разбор `Accept-Language` | `OpenRouterGoalAnalyzerTest`, `MessagesTest` | 11 |
| API | CRUD, авторизация, изоляция, статусы, локализация, AI-контракт | `ApiTest` | 18 |
| E2E | критичные пользовательские сценарии, XSS, прогресс, удаление | `PlaywrightTest` | 6 |

Итого 35 тестов. Пропорция осознанная: большинство ошибок ловится на API/unit-уровне,
UI — только там, где важна сквозная интеграция.

**Вопрос:** почему не автоматизировать всё через UI?
**Ответ:** UI-тесты медленные, хрупкие и дорогие в поддержке. Бизнес-логику и
валидацию быстрее и надёжнее проверять через API. UI — для критичных путей и
интеграции с фронтендом.

## 2. Что автоматизировать (и что нет)

Автоматизируем:

- стабильные, повторяемые сценарии;
- критичные бизнес-пути (логин, CRUD, прогресс);
- регрессию, которая будет гоняться много раз;
- проверки, которые дорого/долго делать руками (изоляция пользователей, локализация,
  XSS, каскадное удаление).

Не автоматизируем (или делаем позже):

- одноразовые проверки;
- исследовательское тестирование и UX;
- внешний вид «на глаз» (нужны visual-тесты, но это отдельная история);
- то, что дешевле проверить на unit-уровне.

## 3. Как в тестах поднимается приложение

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Test(groups = "api")
public class ApiTest extends AbstractTestNGSpringContextTests {

    private static final Path DATABASE = Path.of("target", "test-data", "api.db");

    static {
        Files.deleteIfExists(DATABASE);          // чистая БД до старта контекста
    }

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("app.database.path", DATABASE::toString);
        registry.add("app.ai.api-key", () -> "");
    }
}
```

Разбор:

- `RANDOM_PORT` — Tomcat на свободном порту: можно запускать параллельно и не
  конфликтовать с локальным сервером.
- `@DynamicPropertySource` — подставляет свойства **до** создания контекста
  (в отличие от `@TestPropertySource` с фиксированными значениями).
- Статический блок удаляет файл БД: каждый прогон начинается с чистой схемы.
- `AbstractTestNGSpringContextTests` — мост между TestNG и Spring TestContext:
  Spring-контекст живёт один на класс и кэшируется между тестами.

**Вопрос:** почему не `MockMvc`?
**Ответ:** `MockMvc` не поднимает реальный HTTP-стек. А нам важно проверить заголовки
(`WWW-Authenticate`, `Accept-Language`), статусы, JSON-сериализацию и работу
`HandlerMethodArgumentResolver` так, как это будет в проде. Плата — скорость.

**Вопрос:** почему у API и E2E разные файлы БД?
**Ответ:** чтобы сьюты не влияли друг на друга и могли запускаться в одном JVM
(`-Pall-tests`). `api.db` и `e2e.db` удаляются при загрузке соответствующего класса.

## 4. Изоляция и тестовые данные

Правила, которые применены в проекте:

1. **Каждый тест создаёт своего пользователя** с уникальным email:
   `login-<UUID>@example.com`, `e2e-<nanoTime>@example.com`.
2. **Нет общего состояния** между тестами: нет `static`-полей с данными, нет
   `dependsOnMethods`.
3. **Нет уборки «после»** в большинстве тестов: изолированная БД делает её ненужной.
   Где важно — проверяется явное удаление/каскад.
4. **Порядок не важен**: тесты можно гонять по одному и в любом порядке.
5. **Свои данные на сьют**: отдельные SQLite-файлы.

**Вопрос:** как тестировать изоляцию пользователей?
**Ответ:** создать двух пользователей, у первого создать цель, вторым запросить
`GET /api/goals` — пусто; `PUT/DELETE/analyze` чужой цели — 404. Это есть в
`goalsAreIsolatedBetweenUsers` и `foreignGoalIsNotAccessible`.

**Вопрос:** почему уникальный email, а не удаление пользователя после теста?
**Ответ:** удаление — лишний шаг, который может упасть и «уронить» тест; уникальные
данные проще и надёжнее. В больших системах — фабрики данных + очистка по тегу прогона.

## 5. Три уровня подмены внешнего мира

Внешний AI (OpenRouter) не вызывается ни в одном тесте. Подмена на каждом уровне —
своя:

| Уровень | Инструмент | Где | Что проверяем |
| --- | --- | --- | --- |
| Unit | `com.sun.net.httpserver.HttpServer` | `OpenRouterGoalAnalyzerTest` | формирование запроса, парсинг ответа, коды ошибок |
| API | `@TestConfiguration` + `@Bean @Primary` | `ApiTest.FakeAiConfig` | контракт `/analyze` и сериализацию |
| E2E | `page.route(...).fulfill(...)` | `PlaywrightTest` | рендер анализа и добавление задач |

```java
@TestConfiguration
static class FakeAiConfig {
    @Bean
    @Primary
    GoalAnalyzer fakeGoalAnalyzer() {
        return (goal, language) -> new GoalAnalysis(
                "Нужно постепенно развить выносливость.",
                List.of("Составить план тренировок", "Провести легкую пробежку")
        );
    }
}
```

```java
server = HttpServer.create(new InetSocketAddress("127.0.0.1", 0), 0);
server.createContext("/chat", exchange -> { /* свой ответ и статус */ });
server.start();
```

Почему это сильный ответ на интервью: мы проверяем **свой** код на границе с внешним
сервисом, не завися от его доступности, цены и недетерминированности. И при этом
проверяем настоящий HTTP-клиент, а не мокнутый интерфейс.

## 6. API-тесты: что именно проверяется

- Health: `GET /health` → `{"status":"ok"}`.
- Регистрация/логин: токен, `token_type=bearer`, неверный пароль → 401.
- Дубликат email → 400 + текст.
- Отсутствие пароля → 422.
- CRUD целей и задач, частичное обновление (`PUT` сохраняет опущенные поля).
- `PATCH` и `PUT` для задачи.
- Каскадное удаление цели → задачи тоже удалены.
- Авторизация: без токена → 401 + `WWW-Authenticate: Bearer`; битый токен → 401.
- Изоляция пользователей, чужие цели → 404/403.
- Локализация: `Accept-Language: ru` и `en;q=0.2, ru;q=0.9`.
- AI: `POST /api/goals/{id}/analyze` → `analysis` + `proposed_tasks`.

Технические детали:

- `TestRestTemplate` + Apache `httpclient5` (только тест) — потому что стандартный
  клиент не умеет `PATCH`.
- Ошибки парсятся в `ApiError` (record с полем `detail`).
- Для каждого запроса собираются заголовки: `Content-Type`, `Accept`,
  `Authorization`, `Accept-Language`.

**Вопрос:** почему проверяем и `PUT`, и `PATCH`?
**Ответ:** фронтенд использует PATCH для чекбокса и PUT для полного обновления;
контракт должен поддерживать оба. Это же покрыло регресс после бага с регистрацией
PATCH (см. историю ниже).

## 7. Работа с БД в тестах

- SQLite-файл, схема — `schema.sql` (`CREATE TABLE IF NOT EXISTS`).
- Включены внешние ключи: `SQLiteConfig.enforceForeignKeys(true)`.
- Каскад: `ON DELETE CASCADE` + явное удаление задач в сервисе. Дублирование
  осознанное: БД гарантирует целостность, сервис — предсказуемый ответ API.
- Индексы: `users.email`, `goals.user_id`, `goals.title`, `tasks.goal_id`, `tasks.title`.
- N+1: список целей получает задачи одним JOIN-запросом и группирует в памяти.

**Вопрос:** как проверить, что данные реально записались?
**Ответ:** через API (чтение после записи) — это ближе к поведению пользователя.
Прямой SQL-запрос в тесте — только когда нужно проверить то, чего не видно через API
(например, хэш пароля или каскад на уровне БД).

## 8. CI

`.github/workflows/ci.yml`:

- триггеры: push в `main`, pull request, `workflow_dispatch`;
- два параллельных job'а: API и E2E;
- JDK 25 (Temurin) + кэш Maven;
- E2E: `install --with-deps chromium`, затем `mvn test -Pe2e`;
- артефакты Surefire при любом исходе (`if: always()`);
- `concurrency` отменяет устаревшие прогоны.

**Вопрос:** что важно в CI для E2E?
**Ответ:** headless, фиксированные viewport/locale/timezone, установка браузера с
системными зависимостями, артефакты (trace/screenshot) при падении, разумный таймаут
и параллельность.

## 9. Метрики и отчёты

Что смотрим:

- pass rate и стабильность (flaky rate) по сьютам;
- длительность (API ~секунды, E2E ~десятки секунд);
- покрытие критичных путей, а не «процент строк»;
- escaped defects — баги, которые ушли в прод, хотя тесты были зелёными.

Чего избегаем: гонки за 100% coverage, «зелёные» тесты без ассертов, retry как
способ спрятать проблему.

## 10. Флаки и диагностика

Алгоритм:

1. Воспроизвести локально (headless и headed — поведение может отличаться).
2. Посмотреть trace/скриншот/видео, консоль браузера, сетевые ошибки.
3. Проверить данные: уникальность, порядок, время, локаль.
4. Проверить ожидания: нет ли `sleep`, не гоняемся ли с асинхронным UI.
5. Изолировать: запустить тест отдельно, потом класс, потом сьют.
6. Починить причину; retry — только как временный сигнал.

В проекте для этого есть:

- `page.setDefaultTimeout(15_000)` и явные условия (`awaitText`, `awaitCount`);
- уникальные данные (не пересекаются между прогонами);
- отдельные БД;
- возможность headed-режима (`-Headed`).

## 11. Безопасность: что проверяем и о чём говорить

- **XSS**: пользовательский текст не должен исполняться. E2E-тест подставляет
  `<img onerror=...>` и `<script>...</script>`, проверяет, что нет элементов `img/script`
  и не выставлены флаги в `window`.
- **SQL-инъекции**: параметризованные запросы (`PreparedStatement`).
- **Пароли**: BCrypt, не логируются, не возвращаются в API.
- **JWT**: подпись HS256, срок жизни 30 минут, ключ ≥ 256 бит (SHA-256 от секрета).
- **Авторизация**: чужой ресурс → 404/403, а не «тихо отдаём данные».
- **CORS**: whitelist origins, `allowCredentials` только с конкретными origin.
- **Заголовки**: `WWW-Authenticate` на 401.

**Вопрос:** чем XSS отличается от CSRF?
**Ответ:** XSS — исполнение чужого скрипта в доверенном контексте (кража токена из
`localStorage`); CSRF — запрос от имени пользователя с его cookie без его ведома.
JWT в заголовке (а не в cookie) снижает CSRF-риск, но XSS становится критичнее.

## 13. Три истории багов (готовые ответы на «расскажите о сложном баге»)

### История 1. PATCH возвращал 500

**Симптом:** `PATCH /api/tasks/{id}` → 500, при этом `PUT` работал.
**Диагностика:** в логах `HttpRequestMethodNotSupportedException: Request method 'PATCH'
is not supported`. На методе стояли `@PutMapping` и `@PatchMapping` одновременно.
**Причина:** Spring не объединяет две аннотации отображения на одном методе —
регистрируется только одна (PUT).
**Решение:** `@RequestMapping(value = "/tasks/{taskId}", method = {RequestMethod.PUT, RequestMethod.PATCH})`.
**Профилактика:** тест `patchTaskUpdatesCompletionAndTitle` проверяет и PATCH, и PUT;
добавлен обработчик 405 с локализованным сообщением.

### История 2. Тесты не компилировались из-за `assertThrows`

**Симптом:** 6 ошибок `void cannot be converted to AiException`.
**Причина:** в TestNG `Assert.assertThrows` возвращает `void`, а код присваивал результат.
**Решение:** helper `expectAiException(Runnable)` (или `Assert.expectThrows`).
**Вывод:** API фреймворка надо проверять по javadoc, а не «по памяти из JUnit».

### История 3. CI не запускал `./mvnw`

**Симптом:** локально всё зелёное, в GitHub Actions — `Permission denied`.
**Причина:** проект коммитился с Windows, где у файла нет executable-бита; в git
`mvnw` попал как `100644`.
**Решение:** `git update-index --chmod=+x mvnw` (в индексе стал `100755`).
**Профилактика:** `.gitattributes` с `mvnw text eol=lf`, проверка режима в PR.

## 14. Вопросы по тестовому коду проекта

**Почему API-тесты наследуются от `AbstractTestNGSpringContextTests`?**
Это адаптер Spring TestContext для TestNG: даёт внедрение бинов и кэширование
контекста; без него `@Autowired` в TestNG-классе не сработает.

**Почему `@DynamicPropertySource`, а не `@TestPropertySource`?**
Нужно вычислить путь к БД во время выполнения (`Path.of(...)`) и гарантировать
уникальность. `@DynamicPropertySource` вызывается до создания контекста и принимает
supplier'ы.

**Почему в `ApiTest` есть вложенный `@TestConfiguration`?**
Чтобы подменить только `GoalAnalyzer`, не трогая остальной контекст. `@Primary` — на
случай, если настоящий бин тоже есть.

**Почему fake-анализатор — лямбда, а не класс?**
`GoalAnalyzer` — функциональный интерфейс (один метод). Лямбда короче и явно показывает,
что это стаб.

**Почему в `OpenRouterGoalAnalyzerTest` свой HTTP-сервер, а не Mockito?**
Мы тестируем реальный HTTP-клиент: заголовки, тело, таймауты, коды. Mockito замокал бы
уровень выше и не поймал бы ошибку сериализации/URL.

**Почему порт `0` у `HttpServer`?**
`new InetSocketAddress("127.0.0.1", 0)` — ОС выдаёт свободный порт; тесты не конфликтуют.

**Почему `@AfterMethod(alwaysRun = true)` останавливает сервер?**
Иначе порт/поток останется занятым после упавшего теста, и следующие тесты могут
повести себя нестабильно.

**Почему E2E-тесты не логинятся через API, а регистрируются через UI?**
Так проверяется реальный пользовательский путь (форма, кнопки, появление `#app-screen`)
и заодно создаётся изолированный пользователь. Минус — медленнее; в большом проекте
логин вынесли бы в `storageState`.

**Почему `System.nanoTime()` в именах данных?**
Уникальность без внешних зависимостей; тест можно запускать повторно и параллельно.

**Почему `filter(hasText(...))`, а не `.first()`?**
`first()` зависит от порядка и от данных других тестов; фильтр по уникальному имени
устойчивее.

**Почему в E2E нет `dependsOnMethods`?**
Каждый тест сам создаёт цель и задачу. Независимость важнее «экономии» шагов.

**Почему `page.route` именно с glob `**/api/goals/*/analyze`?**
Совпадает с любым id цели и не требует знать точный URL; при этом не перехватывает
другие запросы.

**Почему проверяется `window.__goalXss`?**
Если бы HTML вставился через `innerHTML`, `onerror` выполнился бы и выставил флаг.
`null` доказывает, что текст отрендерен безопасно.

## 15. Чек-лист ревью автотеста

- [ ] Название теста описывает поведение, а не шаги (`patchTask...`, а не `test1`).
- [ ] Один тест — одна причина падения.
- [ ] Нет `Thread.sleep`, нет магических задержек.
- [ ] Данные уникальны и создаются самим тестом.
- [ ] Нет зависимости от порядка и от других тестов.
- [ ] Ассерты проверяют результат, а не реализацию.
- [ ] Понятное сообщение при падении.
- [ ] Внешние сервисы замоканы или изолированы.
- [ ] Ресурсы закрываются (`try-with-resources`, `@AfterMethod`).
- [ ] Тест падает по правильной причине (проверено мутацией/локально).
- [ ] Нет секретов и реальных токенов в коде.
- [ ] Время выполнения разумно; тяжёлое — в отдельную группу.

## 16. Процессные вопросы-ответы

**Чем smoke отличается от regression?**
Smoke — быстрый набор «система жива» (health, логин, создать цель); regression —
широкий набор проверок перед релизом.

**Как выбрать, что автоматизировать в первую очередь?**
По риску и частоте: критичные бизнес-пути, то, что часто ломается и часто регрессируется.

**Как тестировать API без UI?**
Контракт (метод, путь, статус, схема), авторизация, негативные кейсы, границы,
идемпотентность, локализация, ошибки внешних сервисов.

**Как тестировать интеграцию с внешним сервисом?**
Контракт + моки: unit на клиент, интеграционный тест на стаб-сервер, E2E с моком сети;
отдельно — редкий smoke против реального сервиса (если допустимо).

**Как проверять БД?**
Через API в первую очередь; SQL — для скрытых инвариантов (хэши, каскады, индексы,
миграции). Никогда не полагаться на порядок строк без `ORDER BY`.

**Как тестировать локализацию?**
Подменить `Accept-Language`/`locale` контекста, проверить тексты и форматы; проверить
fallback и q-values (в проекте — `en;q=0.2, ru;q=0.9`).

**Что делать, если тест нестабилен, а времени чинить нет?**
Изолировать (карантин), завести задачу с владельцем и дедлайном, добавить trace/лог,
не удалять проверку. Временный retry — только с тегом и напоминанием.

**Как понять, что тест «не врёт»?**
Проверить, что он падает при поломке (мутация), и что падает по ожидаемой причине;
ассерты должны проверять наблюдаемый результат.
